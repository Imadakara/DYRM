# DYRM — *Do You Read Me?*

Симулятор оператора космической станции лазерной связи. Игра от первого лица на стыке симулятора профессии, пространственной головоломки и диспетчерского менеджмента под давлением времени.

> Этот файл — точка входа в проект. Он описывает замысел, устройство репозиториев, соглашения кодовой базы и процесс работы. На его основе инициализируется `CLAUDE.md`.

---

## 1. О чём игра

**2426 год.** Связь между колониями и кораблями идёт через сеть лазерных ретрансляторов. Каждая станция передаёт сообщение дальше, направляя луч в пределах своего сектора; сообщение проходит длинную цепочку промежуточных узлов. Игрок обслуживает один такой узел.

Станция висит на орбите Нептуна, в 30 астрономических единицах от Солнца. Освещённость здесь в 904 раза ниже земной — Солнце выглядит яркой звездой без диска. Оператор живёт на станции постоянно.

### Игровой цикл

```
Получить сообщение → Проанализировать → Определить адресата → Найти на картах
    → Выбрать лазер → Настроить параметры → Навести луч → Передать → Следующий запрос
```

Адрес — не координаты, а набор данных (`Sector: H-17 / Cluster: Orion / Relay: 8 / Mirror: C`). Игрок расшифровывает его сам, сверяясь с внутриигровыми каталогами. Это ближе к расследованию, чем к вводу цифр.

### Что делает концепцию необычной

В большинстве игр космос — место для полётов или сражений. Здесь космос — инфраструктура связи, а игрок не пилот и не солдат, а оператор узла, от которого зависит работа сектора.

### Жанр и референсы

Simulation · Puzzle · Time Management · Sci-Fi · First Person

По ощущениям: *Papers, Please*, *Signal Simulator*, *Switchboard*, *Event[0]*, *Hardspace: Shipbreaker*, *Keep Talking and Nobody Explodes*. Механика полностью собственная.

### Кривая сложности

| Этап | Состояние мира |
|------|----------------|
| Начало | Всё исправно, несколько десятков адресатов, почти нет ограничений |
| Середина | Отказы оборудования, сотни адресатов, диапазоны, шифрование, очереди, приоритеты |
| Конец | Десятки одновременных лучей, постоянные аварии, нехватка энергии, меняющаяся топология сети |

## 4. Процесс работы

```
ГДД (что за система)  →  ТЗ (как её сделать)  →  Claude Code (реализация)  →  Ревью по критериям приёмки
```

**Одна система из ГДД = один документ ТЗ = одна задача для Claude Code.** Смешивать системы в одной задаче нельзя: границы скоупа — главный инструмент управления качеством.

Каждый ТЗ-документ содержит готовый к копированию промт для Claude Code, самодостаточный без остального документа.

### Именование ТЗ

`ТЗ-NNN — Название.md`, где `NNN` — номер системы из ГДД без точки: `0.1` → `010`, `2.7` → `027`, блок целиком → `000`.

### Скилл `dyrm-tz`

Составление и доработка ТЗ автоматизированы скиллом в `.claude/skills/dyrm-tz/`:

```
.claude/skills/dyrm-tz/
├── SKILL.md                     Процесс, жёсткие правила, как писать промт
├── references/template.md       Канонический шаблон ТЗ (15 разделов)
├── references/godot-mcp.md      Справка по инструментарию — для автора ТЗ
└── scripts/validate_tz.py       Механическая проверка документа
```

Проверка документа:

```bash
python3 .claude/skills/dyrm-tz/scripts/validate_tz.py "путь/к/ТЗ-NNN — Название.md"
```

Скрипт проверяет покрытие требований критериями приёмки, уникальность идентификаторов, самодостаточность промта и согласованность файловых деревьев. Смысловая часть — чек-лист раздела 14 шаблона — проходится глазами.

## 5. Соглашения кодовой базы

Действуют во всём проекте, а не только в отдельных системах.

### Стиль

- **Статическая типизация обязательна** для всех переменных, параметров и возвращаемых значений. `Variant` — только там, где тип действительно неизвестен.
- Каждый скрипт объявляет `class_name`.
- Идентификаторы английские: `snake_case` для функций и переменных, `PascalCase` для классов и узлов.
- Комментарии к формулам и физическим константам — **на русском**.
- Идентификаторы требований в комментариях там, где это помогает: `# FR-12`. Отложенное помечается `TODO(ТЗ-027)` — с указанием, чьё это ТЗ.

### Архитектура

- **Числовые литералы запрещены в скриптах**, кроме универсальных констант (`KM_PER_AU`, `G`, `TAU`). Все параметры живут в ресурсах `.tres`.
- Конфигурация — **плоские типизированные `@export`**. Вложенность `Resource` в `Resource` не глубже одного уровня.
- Проверяемое состояние читается **геттерами** и хранится в публичных свойствах, а не выводится из приватных переменных.
- **Автозагрузки не используются** без явного обоснования в ТЗ. Ссылки между узлами — через `@export var ... : NodePath` или `@onready`.
- Код не полагается на фиксированный список автозагрузок и индексы дочерних узлов корня `SceneTree`: инструментарий инжектирует в проект временную автозагрузку. Обращение к узлам — по имени, группе или экспортированному пути.
- Каждый скрипт парсится независимо. Циклические `preload` и зависимость от автозагрузки на этапе разбора запрещены.
- Никаких аллокаций в горячих циклах `_process`.
- Проект обязан открываться в редакторе **без единой ошибки и предупреждения** в консоли.

### Отладка

- Каждая отладочная команда, повешенная на клавишу, обязана иметь **программный дубль** — публичный метод или Godot-action. Клавиша — сахар, а не единственная точка входа: при запуске в фоновом режиме физический ввод заблокирован.
- Визуальные проверки привязываются к **именованным детерминированным ракурсам**, переключаемым программно.
- Диагностика не существует только в виде `print()`: всё важное дублируется в состояние, читаемое из живого дерева сцены.
- Автоматически проверяемая диагностика выводится в `Control`-узлы, а не только через `_draw()` или 3D-текст.

## 6. Соглашения о координатах и единицах

Зафиксированы в ТЗ-000 и действуют во всех системах, работающих с пространством.

### Единицы

| Величина | Единица |
|----------|---------|
| Длина в сцене | метр = 1 юнит Godot |
| Длина в данных | километр |
| Большие полуоси планет | астрономическая единица, `KM_PER_AU = 149 597 870.7` |
| Время | сутки от эпохи J2000.0 (`epoch_days`) |
| Углы в данных | градусы (в коде немедленно переводятся в радианы) |
| Углы в API | радианы, кроме азимута и возвышения |

### Система координат

Godot: правая система, **+Y вверх**, **−Z вперёд**. Плоскость эклиптики J2000 отображается в плоскость **XZ**:

```
godot_vec = Vector3(ecl.x, ecl.z, -ecl.y)
```

Преобразование существует **ровно в одной функции** `OrbitalMath.ecliptic_to_godot()` и нигде не дублируется.

### Базис наведения

Локальный базис `Station/AimingReference` на неподвижной ферме станции:

- **+Y** — от центра Нептуна к станции (местный зенит)
- **−Z** — по вектору орбитальной скорости
- **+X** — дополняет до правой тройки

**Азимут** — в плоскости XZ от −Z по часовой стрелке при взгляде с +Y, диапазон [0°, 360°). **Возвышение** — угол над плоскостью XZ, диапазон [−90°, +90°].

### Почему это важно

Вся игра построена на том, что игрок направляет луч в конкретную точку пространства. Направления на объекты обязаны быть настоящими: если каталог говорит «Уран, азимут 143°», луч, повёрнутый на 143°, должен указывать на нарисованный Уран. Любое упрощение масштаба обязано сохранять направление точным.

## 7. Инструментарий

Разработка ведётся Claude Code с двумя подключёнными MCP-серверами.

| Сервер | Роль | Класс операций |
|--------|------|----------------|
| [`Erodenn/godot-mcp-runtime`](https://github.com/Erodenn/godot-mcp-runtime) | основной | Headless-редактирование сцен, узлов, свойств, скриптов, сигналов, автозагрузок; поиск по проекту; валидация до запуска. Плюс живой мост в запущенный проект: скриншоты, симуляция ввода, обход дерева сцены, выполнение GDScript в контексте `SceneTree` |
| [`Coding-Solo/godot-mcp`](https://github.com/Coding-Solo/godot-mcp) | вспомогательный | Запуск редактора и проекта, чтение вывода, управление UID (Godot 4.4+) |

Правило по умолчанию: работать через runtime-сервер; ко второму обращаться за UID-операциями и как к резервному пути запуска.

Мост реализован как временная автозагрузка с TCP-слушателем на localhost. Она инжектируется при запуске и снимается при остановке — следов в репозитории не остаётся.

**Ограничения, влияющие на планирование.** Мост работает только с запущенным проектом, поэтому проект обязан запускаться после каждого этапа работ. В фоновом режиме окно уводится за пределы экрана и физический ввод блокируется. Чтение вывода недоступно при подключении к внешне запущенному процессу.

Требования к архитектуре, вытекающие из инструментария, собраны в разделе 5 выше и в разделе 7.7 шаблона ТЗ.

## 11. Инициализация проекта

Порядок первого запуска работ:

1. Прочитать `DYRM Docs/Идея игры - DYRM.md` и `DYRM Docs/ГДД - Перечень систем.md`.
2. Прочитать `DYRM Docs/ТЗ/ТЗ-000 — Игровое окружение.md` целиком.
3. Взять промт из раздела 13 этого ТЗ и выполнить его по этапам Э1–Э9. Учесть, что `project.godot` уже существует — этап Э1 сводится к структуре папок и `main.tscn`.
4. После каждого этапа проект обязан запускаться без ошибок.
5. По завершении прогнать автотесты и пройти визуальный чек-лист раздела 10 ТЗ.

Команда автотестов задаётся в ТЗ-000:

```bash
godot --headless --path . --script res://tools/run_tests.gd
```

Ожидаемый вывод — строка на тест и финальное `RESULT: <N> passed, 0 failed`, код возврата 0.
