# Составление ТЗ для DYRM

## Что это за документ

ТЗ проекта DYRM — это документ, из которого Claude Code реализует **одну** игровую систему из ГДД без дополнительных вопросов. Он одновременно:

- фиксирует дизайн-решения и их обоснование (для человека, надолго);
- задаёт проверяемые границы (для ревью);
- содержит готовый к копированию промт (для исполнителя).

Шаблон — `references/template.md`. Он **канонический**: копия в `DYRM Docs/ТЗ/_ШАБЛОН ТЗ.md` — зеркало для чтения. Правки шаблона вносятся здесь, затем зеркало обновляется.

## Источники истины

Читать **до** начала работы, всегда:

| Файл | Что берём |
|------|-----------|
| `DYRM Docs/ГДД - Перечень систем.md` | Дословную формулировку системы, её приоритет, соседние системы |
| `DYRM Docs/Идея игры - DYRM.md` | Замысел, ощущение, референсы, состав MVP |
| `DYRM Docs/ТЗ/ТЗ-*.md` | Уже принятые решения, занятые ID, установленные контракты API |
| Репозиторий `DYRM` | Что уже реализовано на самом деле |

Расхождение между ГДД и уже написанным ТЗ — это находка, а не помеха. Вынести в раздел 11 как открытый вопрос.

## Процесс

### 1. Собрать контекст

Прочитать источники выше. Выписать: номер системы, приоритет, соседние системы, которые легко спутать со скоупом, и все ТЗ, чей публичный API придётся соблюсти.

### 2. Уточнить у пользователя

Спросить **до** написания, а не после, всё, что меняет архитектуру: технические развилки, уровень упрощения, спорные дизайн-решения. Не спрашивать то, что выводится из ГДД или из уже написанных ТЗ.

### 3. Проверить фактуру

Любое число, попадающее в документ, должно иметь источник или расчёт. Физические константы, орбитальные элементы, справочные величины — проверять по первоисточнику, а не по памяти. Формулы — **посчитать скриптом** и вставить в документ полученные значения как проверочные примеры. Эти же значения потом становятся автотестами.

Правило: если число нельзя проверить, оно не число, а допущение — и живёт в таблице 2.3.

### 4. Заполнить шаблон

Скопировать `references/template.md`, заполнить разделы 0–12, удалить все подсказки `> 💡`. Раздел 13 — **последним**.

### 5. Написать промт

См. «Как писать промт» ниже. Это самая ответственная часть.

### 6. Прогнать проверку

```bash
python3 scripts/validate_tz.py "путь/к/ТЗ-NNN — Название.md"
```

Скрипт проверяет механику: покрытие FR критериями, уникальность ID, баланс код-блоков, самодостаточность промта, согласованность файловых деревьев. Он **не** проверяет смысл — раздел 14 шаблона проходится глазами отдельно.

### 7. Положить и отдать на ревью

Файл кладётся в `DYRM Docs/ТЗ/` под именем `ТЗ-NNN — Название.md`.

Именование: `NNN` — номер системы из ГДД без точки. `0.1` → `010`, `2.7` → `027`, блок целиком → `000`.

В ответе пользователю — не пересказ документа, а **список решений, которые стоит оспорить**: развилки, где выбор был неочевиден, и риски, которые проявятся на реализации.

## Жёсткие правила

Эти пять ошибок повторяются чаще всего.

**1. Скоуп течёт.** Раздел 2.2 «Явно НЕ входит в скоуп» — не формальность. Для каждой соседней системы из ГДД, которую можно спутать с текущей, нужна строка с указанием её ТЗ. Если раздел 2.2 короче раздела 2.1 — он написан плохо.

**2. Требование непроверяемо.** Каждое FR — одно утверждение, у которого есть критерий приёмки. «Система должна быть производительной» — не требование. «≥60 FPS в 1920×1080 в каждом из пяти именованных ракурсов» — требование.

**3. Промт не самодостаточен.** Промт не имеет права ссылаться на «раздел 6 выше». Все числа, формулы, имена файлов и сигнатуры — внутри промта. Проверка: прочитать промт, закрыв остальной документ. Если возник вопрос — промт неполон.

**4. Число без происхождения.** У каждой величины в разделе 6 — источник, расчёт или пометка «дизайнерский выбор». Число, взятое из воздуха, разойдётся с реализацией и никто не поймёт, кто прав.

**5. Инструментарий описан слишком подробно.** См. следующий раздел.

## Про Godot MCP

Разработку ведёт Claude Code с двумя MCP-серверами (описание — `references/godot-mcp.md`). В ТЗ про них пишется **мало и только по делу**.

**Что пишем:** архитектурные следствия. Инструментарий умеет читать свойства узлов, выполнять GDScript в живом дереве, снимать скриншоты, симулировать ввод, валидировать скрипты до запуска. Из этого следуют конкретные требования к архитектуре — плоские `@export`-параметры, состояние через геттеры, программные дубли отладочных клавиш, именованные ракурсы, независимо парсируемые скрипты. Всё это — раздел 7.7.2 шаблона, и оттуда оно расходится по разделам 6.2, 7.3, 7.4 и по критериям приёмки.

**Чего не пишем:** списков инструментов, их параметров, порядка вызовов, инструкций по установке и настройке. Исполнитель знает свои инструменты лучше, чем автор ТЗ. ТЗ отвечает на вопрос «что должно получиться», а не «какой кнопкой».

**Проверка соразмерности:** если из ТЗ убрать все упоминания MCP, документ должен остаться полностью осмысленным и реализуемым — просто менее удобным в проверке. Если он разваливается, значит инструментарий описан не на своём уровне.

## Как писать промт

Промт живёт в разделе 13, в блоке с четырьмя обратными кавычками (внутри него бывают обычные трёхкавычные блоки с кодом).

Порядок блоков — не менять, он отлажен:

1. **Задача** — три-четыре предложения: что за игра, что за система, каково исходное состояние репозитория.
2. **Стек и жёсткие ограничения** — версия движка, язык, стиль кода, запреты уровня «никаких autoload», «числовые литералы только в ресурсах».
3. **ЧЕГО ДЕЛАТЬ НЕЛЬЗЯ** — нумерованный список с указанием, чьё это ТЗ. Самый изнашиваемый блок промта: если исполнитель вылезает за скоуп, усиливать надо здесь. Заканчивается инструкцией «возник соблазн сделать заодно — не делай, запиши в отчёт».
4. **Соглашения** — координаты, единицы, оси, направления. С пометкой «ЗАФИКСИРОВАНО, не менять».
5. **Спецификации** — модели, формулы, таблицы данных, эталонные значения. Каждая формула сопровождается проверочными числами.
6. **Обязательный публичный API** — точные сигнатуры, с пометкой, что менять их нельзя, потому что на них рассчитывают другие ТЗ.
7. **Файловая структура** — полное дерево, «создать ровно это».
8. **Порядок работы по этапам** — с требованием, чтобы проект запускался после каждого.
9. **Автотесты** — команда запуска, формат вывода, нумерованный список обязательных тестов с допусками.
10. **Что делать при неоднозначности** — «выбери простейшее решение, проходящее тесты, и запиши выбор в отчёт; не останавливайся с вопросом; не расширяй скоуп». Отдельно: «если требование противоречит само себе — остановись и опиши противоречие».
11. **Отчёт по завершении** — нумерованный список пунктов: сделано, результат тестов, отклонения, неоднозначности, отложено, что проверить глазами, метрики.

Тон промта — инструкция, а не просьба. Императив, без «пожалуйста» и без «постарайся».

Проверочные значения в промте дублируют раздел 6 документа намеренно. Это не избыточность, а страховка: промт уедет в другой контекст без документа.

## Доработка существующего ТЗ

Не переписывать целиком. Порядок:

1. Прочитать текущую версию и понять, какие ID уже заняты.
2. Внести изменения точечно. **Номера удалённых пунктов не переиспользовать.**
3. Синхронизировать промт с изменениями в разделах 1–12 — это забывают чаще всего.
4. Поднять версию в паспорте, добавить строку в раздел 15 «История изменений».
5. Прогнать `validate_tz.py` и чек-лист раздела 14.

Если изменение затрагивает публичный API — проверить, не сломает ли оно ТЗ из строки «Блокирует ТЗ» паспорта, и отметить это в ответе.
