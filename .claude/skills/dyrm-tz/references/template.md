# ТЗ-NNN — «Название системы»

> **Как пользоваться шаблоном.**
> 1. Скопировать файл в `DYRM Docs/ТЗ/` под именем `ТЗ-NNN — Название.md`, где `NNN` — номер системы из ГДД без точки (`0.1` → `010`, `2.7` → `027`, блок 0 целиком → `000`).
> 2. Заполнить разделы **1–12**. Раздел **13 (промт)** пишется **последним** и должен быть выжимкой из разделов 1–12, самодостаточной без остального документа.
> 3. Все инструкции-подсказки (текст в блоках `> 💡`) удалить из готового документа.
> 4. Правило нумерации: `FR-xx` — функциональные требования, `NFR-xx` — нефункциональные, `DM-xx` — модель данных, `AC-xx` — критерии приёмки, `R-xx` — риски, `Q-xx` — открытые вопросы. Номера **не переиспользуются** после удаления пункта.
> 5. Приоритет каждого требования: **MUST** (без него система не принимается) · **SHOULD** (нужно, но можно во второй итерации) · **COULD** (по возможности) · **WON'T** (явно отложено).

### 7.7. Инструментальная среда: Godot MCP

> 💡 **Уровень детализации этого раздела строго ограничен.**
> Здесь описывается только то, что **влияет на архитектуру и связи объектов**. Конкретные вызовы инструментов, их параметры, порядок установки и настройки в ТЗ **не пишутся** — это среда исполнения, а не предмет технического задания. Задача раздела — заранее снять барьеры, а не научить пользоваться инструментом.

#### 7.7.1. Что доступно

Разработка ведётся Claude Code с подключёнными двумя MCP-серверами:

| Сервер | Роль | Класс операций |
|--------|------|----------------|
| [`Erodenn/godot-mcp-runtime`](https://github.com/Erodenn/godot-mcp-runtime) | **основной** | Headless-редактирование сцен и узлов, свойства, скрипты, сигналы, автозагрузки, настройки проекта, поиск по проекту, валидация до запуска, батч-операции. Плюс **живой мост** в запущенный проект: скриншоты, симуляция ввода, обход дерева сцены, выполнение произвольного GDScript в контексте `SceneTree` |
| [`Coding-Solo/godot-mcp`](https://github.com/Coding-Solo/godot-mcp) | **вспомогательный** | Запуск редактора и проекта, чтение вывода, базовое создание сцен и узлов, экспорт `MeshLibrary`, **управление UID** (`get_uid`, `update_project_uids`, Godot 4.4+) |

Функциональность серверов пересекается. Правило по умолчанию: **всё через runtime-сервер**, к `Coding-Solo/godot-mcp` обращаться за UID-операциями и как к резервному пути запуска.

Мост в запущенный проект реализован как временная автозагрузка `McpBridge` с TCP-слушателем на localhost. Она появляется при запуске через MCP и снимается при остановке — в репозитории её следов не остаётся.

#### 7.7.2. Требования к архитектуре, вытекающие из инструментария

> 💡 Эта таблица — обязательная часть каждого ТЗ. Строки, неприменимые к конкретной системе, удаляются; остальные уточняются под неё.

| Возможность среды | Что она требует от архитектуры системы |
|-------------------|----------------------------------------|
| Выполнение произвольного GDScript в живом дереве сцены | Публичный API системы достижим от корня коротким детерминированным путём либо через `class_name` и группы. Любое проверяемое состояние читается **геттером**, а не выводится из приватных переменных |
| Чтение дерева сцены и свойств узлов | Проверяемые величины живут в `@export`/публичных свойствах узлов, а не только в локальных переменных методов |
| Программная правка свойств и добавление узлов | Конфигурация — **плоские типизированные `@export`**. Вложенность `Resource` в `Resource` — не глубже одного уровня, иначе параметр становится недоступен для автоматической правки |
| Скриншот запущенного проекта | Каждый визуальный критерий приёмки привязан к **именованному детерминированному ракурсу**. Набор ракурсов задаётся в ТЗ явно и переключается программно |
| Фоновый режим запуска (окно за пределами экрана, физический ввод заблокирован) | Любая отладочная команда, повешенная на клавишу, обязана иметь **программный дубль** — публичный метод или Godot-action. Клавиша — сахар, а не единственная точка входа |
| Обход видимых `Control`-узлов | Диагностика, которую нужно проверять автоматически, выводится в `Control`-узлы (`Label` и т. п.), а не только через `_draw()` или 3D-текст |
| Валидация скриптов и сцен до запуска | Каждый скрипт парсится независимо. Циклические `preload`, зависимость от автозагрузки на этапе разбора — запрещены |
| Временная автозагрузка моста | Код не полагается на фиксированный список автозагрузок, их порядок и индексы дочерних узлов корня `SceneTree`. Обращение к узлам — по имени, группе или экспортированному `NodePath` |
| Поиск по исходникам проекта | Соглашения именования однозначно грепаемы: идентификаторы требований в комментариях (`# FR-12`), маркеры отложенного (`TODO(ТЗ-027)`) |
| Чтение вывода недоступно при подключении к внешне запущенному процессу | Диагностика не существует только в виде `print()`. Всё важное дублируется в состояние, читаемое из живого дерева |
| Батч-операции над сценами | Сцены собираются декларативно. Процедурная генерация геометрии в коде предпочтительнее ручного дерева из сотен узлов |
| Наличие инструментов управления автозагрузками | **Не является аргументом за автозагрузки.** Решение остаётся архитектурным и обосновывается в 7.6 |

#### 7.7.3. Ограничения, которые нужно учесть в плане работ

| Ограничение | Следствие для ТЗ |
|-------------|------------------|
| Мост работает только с запущенным проектом | Этапы (раздел 12) строятся так, чтобы проект запускался после каждого из них — иначе рантайм-проверки недоступны |
| Скриншот отражает то, что реально отрисовано | Ракурсы должны показывать проверяемое, а не «общий вид» |
| Симуляция ввода батчами с задержками | Сценарии проверки описываются как последовательность шагов с ожидаемым состоянием после каждого, а не как «понажимать и посмотреть» |

## 13. Промт для Claude Code

> **Правила для этого раздела.**
> - Промт даётся **одним блоком**, готовым к копированию.
> - Промт **самодостаточен**: он не ссылается на «раздел 6 выше», а содержит все нужные числа, формулы и имена файлов внутри себя.
> - Промт содержит: роль и контекст → жёсткие ограничения → пошаговый план → полные спецификации → критерии готовности → порядок самопроверки → что делать при неоднозначности.
> - Промт **запрещает** выходить за скоуп: список «не делай» обязателен.
> - Промт **называет** доступные MCP-серверы и класс операций каждого, но **не учит ими пользоваться**: ни списка инструментов, ни параметров, ни порядка вызовов. Исполнитель знает свои инструменты лучше, чем автор ТЗ.
> - Из раздела 7.7 в промт переносятся только **архитектурные следствия** (плоские `@export`, программные дубли отладочных команд, именованные ракурсы, независимая парсируемость скриптов и т. п.) — как обычные требования, без упоминания, что они продиктованы инструментарием.
> - Промт заканчивается требованием отчёта: что сделано, что отклонено от ТЗ и почему.
