# Тест-кейсы ТЗ-100 — Игрок и станция от первого лица

Карточки по шаблону `references/test-case-template.md`. Покрывает критерии приёмки типа
«рантайм-авто» и «визуально» из ТЗ-100 (полный текст — сестринский репозиторий `DYRM Docs`,
`ТЗ/ТЗ-100 — Игрок и станция от первого лица.md`, разделы 10.1/10.3/10.4) плюс регресс-чеклист
уже известных отклонений (раздел 16 того же документа). Тип «авто» — это `tools/run_tests.gd`
(`T-20…T-40`), сюда не входит.

Сцена по умолчанию — `scenes/dev/movement_calibration.tscn` (полная станция без слоя Deep и
пресетов ТЗ-000, грузится быстрее `main.tscn`).

**Гантелеобразная станция (ТЗ-000 §17, 2026-07-30) — `main.tscn` больше не грузит эту
топологию.** `main.tscn` теперь указывает на `scenes/station_dumbbell/station_dumbbell.tscn`
(неподвижный ствол antenna/hub/transmission без гравитации + вращающийся барабан с
жилым/рабочим плечом, 0,3g) — узлов `control_deck`/`corridor_a`…`corridor_d`/`SpokeHatch`/
`WorkPanel`/`Door`, на которых построен весь этот каталог, там нет вовсе. `player_controller.gd`
адаптирован под новую топологию отдельной ревизией (кинематический пол на плечах, свободный
полёт в стволе, `begin_transition()` между ними) и покрыт `tools/run_tests.gd` T-20…T-42
(player_locomotion), а не этим каталогом — см. `CLAUDE.md`, таблица блоков автотестов.
`movement_calibration.tscn` **не тронута** и по-прежнему грузит старое кольцо
(`scenes/station/station.tscn`) — все карточки ниже (контракты Door/SpokeHatch/WorkPanel,
ракурсы P1…P6, регресс-чеклист R1…R6) остаются валидными именно для НЕЁ, отдельно от активной
игровой сцены. Перенос панелей/дверей/люков на гантелеобразную станцию — сознательно отложенная,
ещё не начатая задача (см. `run_tests.gd`: `interaction_ui` целиком пропускается на дамбелле с
сообщением `SKIP interaction_ui: панели/двери/люки не размещены...`) — эта задача добавит НОВЫЕ
карточки под новую топологию, а не заменит карточки этого файла (они не станут неактуальными,
пока `station.tscn`/`movement_calibration.tscn` существуют и используются для регрессии).

**Двери убраны из `station.tscn`** (владелец проекта, 2026-07-29): створка (1,6×2,3 м) не
перекрывала проём стыка арок геометрически (7×3,5 м, без торцевой стены — см. TC-ТЗ100-R5 ниже,
статус «снято»), и её основной эффект был не «непроходимо без взаимодействия», а спорадический
силовой толчок игрока назад при столкновении капсулы со створкой по центру прохода (артефакт
`move_and_slide()`/Jolt, не сама геометрия — см. `ТЗ-100.md §16.1`). Класс `Door`
(`src/interaction/door.gd`, `scenes/interaction/door.tscn`) остался рабочим и покрыт тестами —
просто больше не размещён на станции; тесты, которым нужен экземпляр двери (T-36, T-37,
TC-ТЗ100-02), создают одноразовую фикстуру, а не ссылаются на узел сцены.

## Два уровня проверки: контракт взаимодействия vs локомоция

Не проверяй каждый AC полной пешей навигацией от точки спавна до цели — геометрия кольца
(радиальное «вверх», тангенциальное «вперёд», глобальная **Y** как ось вправо/влево поперёк
коридора) делает вычисление «точки в 1,2 м перед панелью» и разворот к ней неожиданно хрупким
упражнением. Спецификация верифицировала большинство рантайм-авто критериев именно так — двумя
раздельными приёмами:

1. **Контракт взаимодействия (Door/SpokeHatch/WorkPanel) — вызывай методы объекта напрямую**,
   без игрока и `InteractionProbe` (см. TC-ТЗ100-03/04/05 ниже). Так проверено и в самой
   ТЗ-100 (§16.3–16.4).
2. **Локомоция (дрейф, азимут, ступени, дистанция взаимодействия) — только тут действительно
   нужен игрок и `simulate_input`/программные дубли движения.** Правила:
   - Сравнивай `player.position` (локальная система `RotatingRing`), а не
     `player.global_position` — кольцо крутится непрерывно, и `global_position` меняется
     каждый кадр от одного только вращения родителя. Для другого узла кольца в той же системе
     — `station.get_rotating_ring().to_local(node.global_position)`.
   - «Вверх» (`up_local`) — радиальный вектор в плоскости **XZ** (к оси вращения); «вперёд» —
     тангенциальный, тоже в XZ; «вправо»/страф игрока (`basis.x`) — это глобальная **Y**
     (боковая ширина коридора, 4,5 м). Раскладывать вектор «куда идти» на эти три компоненты
     вручную — рабочий, но хрупкий путь; для проверки контракта он не нужен (см. пункт 1).

Именованные ракурсы ТЗ-100 §10.3 (`P1_ring_ahead` … `P6_hatch`) не имеют зафиксированных
координат в спецификации («телепорт + направление взгляда» — без чисел) — практический путь:
люки стоят прямо в тангенциальном пути обхода кольца, туда доходит простая ходьба вперёд с
проверкой `InteractionProbe.get_target()`; для двери (после удаления из сцены, см. выше) нужна
фикстура тем же приёмом, что в T-36/T-37 (`tools/run_tests.gd`); панели — на боковой стене, для
них надёжнее либо ручной подбор ракурса (`set_look_direction` + `take_screenshot`, несколько
попыток), либо прямая проверка контракта без скриншота (см. TC-ТЗ100-11).

extends RefCounted
func execute(scene_tree: SceneTree) -> Variant:

	var content: Control = panel.get_ui_root()
	var button: Button = content.get_node("%CounterButton")
	var rect: Rect2 = button.get_global_rect()
	var center_px: Vector2 = rect.position + rect.size * 0.5
	var config: PanelConfig = panel.config
	var u: float = center_px.x / config.viewport_size_px.x
	var v: float = center_px.y / config.viewport_size_px.y
	var local_x: float = (u - 0.5) * config.surface_size_m.x
	var local_y: float = (0.5 - v) * config.surface_size_m.y
	var world_point: Vector3 = panel.to_global(Vector3(local_x, local_y, 0.0))
	var before: int = content.get_press_count()

	panel.receive_click(true)
	panel.receive_click(false)
	return {"before": before, "after": content.get_press_count()}

пиксель в локальную точку поверхности панели.

**Ожидаемый результат** — счётчик нажатий увеличивается ровно на 1.

**Фактический результат** — `press_before: 0, press_after: 1`.
