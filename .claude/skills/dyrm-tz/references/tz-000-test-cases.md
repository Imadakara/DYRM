# Тест-кейсы ТЗ-000 — Игровое окружение

Карточки по шаблону `references/test-case-template.md`. Покрывает критерии приёмки типа
«рантайм-авто» и «визуально» из ТЗ-000 (полный текст — сестринский репозиторий `DYRM Docs`,
`ТЗ/ТЗ-000 — Игровое окружение.md`, раздел 10.1). Тип «авто» — это `tools/run_tests.gd`
(`T-01…T-19`), сюда не входит.

Сцена по умолчанию — `main.tscn` (единственная сцена с `DebugFlyCamera`/`CameraPresets` —
слоем Deep и всеми 10 небесными телами; `movement_calibration.tscn` его не содержит).

**Важная находка (2026-07-28), актуальна для всех визуальных карточек ниже**: в `main.tscn`
`Main/MainCamera` (`DebugFlyCamera`) больше не является активной камерой вьюпорта —
`main_cam.current == false`, а `get_viewport().get_camera_3d()` возвращает
`PlayerCamera` игрока (добавлен ТЗ-100). `go_to_preset()`/`current_preset()` продолжают
корректно менять и читать состояние самого узла `DebugFlyCamera` (числовой контракт AC-50
работает), но результат не виден на экране — скриншот показывает вид глазами игрока, а не
запрошенный пресет. Принудительная установка `main_cam.current = true` немедленно чинит
рендер (геометрия и освещение ТЗ-000 в порядке — проверено), то есть баг именно в том, что
ничто не переключает активную камеру, а не в самой геометрии. Похоже на кросс-ТЗ-регрессию:
ТЗ-000 верифицировался, когда игрока ещё не было и `MainCamera` была единственной камерой;
ТЗ-100 добавила вторую камеру, ничего не сделав, чтобы явно управлять тем, какая из них
активна (тот же корень, что и известный ❌ по `FR-51` ТЗ-100 — отсутствие переключения между
камерами — но здесь следствие серьёзнее: ломается не только ручное переключение, а весь
визуальный набор проверок ТЗ-000). Не задокументировано ни в одном из разделов 16 обоих ТЗ на
момент находки — стоит обсудить с пользователем и решить, чьё это ТЗ чинить (скорее всего
ТЗ-100, раз она внесла вторую камеру, но решение — не мне принимать единолично).

**Предусловия** — проект запущен со сценой `main.tscn`; узел `Main/MainCamera`

**Шаги**
```gdscript

func execute(scene_tree: SceneTree) -> Variant:

extends RefCounted

	var clock := scene_tree.root.get_node("Main/GameClock")
	var station := scene_tree.root.get_node("Main/Station")
	return {

```

**Ожидаемый результат** — значения в тексте `*_label` совпадают (с учётом округления в

**Фактический результат** — `epoch_label`/`time_scale_label`/`station_pos_label` совпадают с

### TC-ТЗ000-03 — `time_scale` и пауза двигают/не двигают время

| Поле | Значение |
|---|---|
| Источник | ТЗ-000, `AC-52` (`FR-53`) |
| Тип | рантайм-авто |
| Сцена | `scenes/main.tscn` |
| Статус | ✅ проходит |
| Дата последнего прогона | 2026-07-28 |

**Предусловия** — проект запущен.

**Шаги**
```gdscript
extends RefCounted
func execute(scene_tree: SceneTree) -> Variant:
	var clock := scene_tree.root.get_node("Main/GameClock")
	clock.time_scale = 10000.0
	clock.paused = false
	var before_running: float = clock.epoch_days
	for i in range(30):
		await scene_tree.physics_frame
	var after_running: float = clock.epoch_days
	clock.paused = true
	var before_paused: float = clock.epoch_days
	for i in range(30):
		await scene_tree.physics_frame
	var after_paused: float = clock.epoch_days
	return {
		"delta_running": after_running - before_running,
		"delta_paused": after_paused - before_paused,
	}
```

**Ожидаемый результат** — `delta_running > 0` (пропорционально `time_scale`); `delta_paused
== 0.0` ровно.

**Фактический результат** — `delta_running: 0.0559` (30 физкадров ≈0,5 с реального времени ×
10000 ÷ 86400 с/сут ≈ 0,058 сут — совпадает с точностью до дрожания частоты кадров),
`delta_paused: 0.0` ровно.

**Чек-лист прогона**
- [x] Перед стартом проверено, что не висит Godot от предыдущего запуска
- [x] Сразу после `run_project` проверен `get_debug_output` — ошибок нет
- [x] Нестандартные типы возврата в `run_script` — явно типизированы
- [x] Сессия завершена `stop_project`
- [x] Фактический результат сверен с ожидаемым — совпадает, расхождений нет

| Сцена | `scenes/main.tscn` |
| Статус | не запускался |
| Дата последнего прогона | — |

**Предусловия** — проект запущен, `run_project(background: false)` — фоновый режим не
создаёт целевой GPU-нагрузки, число будет заниженным и неинформативным (см. `SKILL.md` общего
скилла). **Дополнительно** (см. находку в начале файла): пока `MainCamera.current == false`,
FPS будет одинаковым во всех пяти пресетах, потому что реально рендерится вид `PlayerCamera`,
а не запрошенный пресет — если результат «не меняется от пресета к пресету», это не значит,
что сцена одинаково тяжела в каждом ракурсе, значит рендерится не то, что запрошено.

**Шаги** — для каждого `i` в `1..5`: `cam.go_to_preset(i)`, ~60 физкадров на устаканивание,
прочитать `Engine.get_frames_per_second()`.

**Ожидаемый результат** — ≥60 FPS в 1920×1080 в каждом пресете.
