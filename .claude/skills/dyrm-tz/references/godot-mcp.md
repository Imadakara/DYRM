# Godot MCP: справка для автора ТЗ

> Этот файл — **для автора ТЗ**, а не для копирования в ТЗ. Он нужен, чтобы понимать, какие проверки в принципе возможны, и формулировать требования так, чтобы они были проверяемы. В сам документ переносятся только архитектурные следствия (таблица 7.7.2 шаблона).

## Два сервера

### `Erodenn/godot-mcp-runtime` — основной

https://github.com/Erodenn/godot-mcp-runtime

Умеет всё, что нужно в обычной работе, и главное — имеет **живой мост в запущенный проект**. Мост реализован как временная автозагрузка `McpBridge` с TCP-слушателем на localhost; она инжектируется при запуске и снимается при остановке, следов в репозитории не остаётся.

Классы операций:

| Класс | Что доступно |
|-------|--------------|
| Управление проектом | Запуск редактора и проекта, подключение к внешне запущенному экземпляру, остановка, отключение, чтение вывода, метаданные проекта |
| Рантайм | Скриншот вьюпорта, симуляция ввода (клавиши, мышь, клики по элементам, Godot-actions, паузы), обход видимых `Control`-узлов, **выполнение произвольного GDScript с полным доступом к `SceneTree`** |
| Редактирование сцен | Создание сцен, добавление узлов, текстуры, сохранение и save-as, экспорт `MeshLibrary`, батч-операции |
| Редактирование узлов | Чтение дерева сцены, чтение и запись свойств, привязка скриптов, дублирование, удаление, работа с сигналами |
| Конфигурация проекта | Автозагрузки (список, добавление, удаление, правка), настройки проекта, дерево файлов, поиск по исходникам, зависимости сцены |
| Валидация | Проверка синтаксиса скриптов и ссылок на ресурсы **до** запуска |

### `Coding-Solo/godot-mcp` — вспомогательный

https://github.com/Coding-Solo/godot-mcp

Пересекается с runtime по базовым операциям (запуск, вывод, создание сцен и узлов, `MeshLibrary`). Уникален тем, что умеет **управление UID** — получение UID файла и перезапись UID-ссылок по проекту (Godot 4.4+).

Правило по умолчанию: работать через runtime; сюда обращаться за UID-операциями и как к резервному пути запуска.

## Что из этого следует для ТЗ

Каждая строка — возможность среды и вытекающее из неё требование к архитектуре.

| Среда умеет | Значит, в ТЗ должно быть |
|-------------|--------------------------|
| Выполнять GDScript в живом дереве | Публичный API достижим от корня коротким путём или через `class_name`/группы; проверяемое состояние читается геттерами |
| Читать дерево и свойства узлов | Проверяемые величины — в `@export`/публичных свойствах, а не в локальных переменных |
| Программно править свойства | Конфигурация — плоские типизированные `@export`; вложенность `Resource` в `Resource` не глубже одного уровня |
| Снимать скриншоты | Именованные детерминированные ракурсы, переключаемые программно; визуальные AC привязаны к ним |
| Симулировать ввод, в т. ч. в фоне (физический ввод заблокирован) | Каждая отладочная команда на клавише имеет программный дубль — метод или Godot-action |
| Обходить видимые `Control`-узлы | Автоматически проверяемая диагностика выводится в `Control`, а не только через `_draw()` или 3D-текст |
| Валидировать скрипты до запуска | Каждый скрипт парсится независимо; циклические `preload` и зависимость от autoload на этапе разбора запрещены |
| Инжектировать временную автозагрузку | Код не полагается на фиксированный список автозагрузок и индексы детей корня `SceneTree` |
| Искать по исходникам | Грепаемые соглашения: `# FR-12` в комментариях, `TODO(ТЗ-027)` для отложенного |
| Работать с автозагрузками | **Не аргумент за автозагрузки** — решение остаётся архитектурным |

## Ограничения, влияющие на план работ

| Ограничение | Следствие |
|-------------|-----------|
| Мост работает только с запущенным проектом | Проект обязан запускаться после каждого этапа, иначе рантайм-проверки недоступны |
| Чтение вывода недоступно при подключении к внешне запущенному процессу | Диагностика не живёт только в `print()`; всё важное дублируется в читаемое состояние |
| Фоновый режим уводит окно за пределы экрана и блокирует физический ввод | Проверки не могут зависеть от реального нажатия клавиш |
| Скриншот показывает то, что реально отрисовано | Ракурс должен показывать проверяемое, а не «общий вид» |
| Симуляция ввода идёт батчами с задержками | Сценарий проверки — последовательность шагов с ожидаемым состоянием после каждого |

## Уровень детализации в ТЗ

**Пишем:** «Каждая отладочная команда, повешенная на клавишу, обязана иметь программный дубль — публичный метод или Godot-action».

**Не пишем:** «Вызвать `simulate_input` с массивом событий типа `key`, затем `take_screenshot` с `responseMode: 'full'`».

Проверка соразмерности: убрать из ТЗ все упоминания MCP. Документ обязан остаться осмысленным и реализуемым — просто менее удобным в проверке. Если разваливается — уровень выбран неверно.
