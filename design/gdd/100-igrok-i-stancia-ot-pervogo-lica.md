## Overview

Игрок присутствует на станции как физическое тело (`CharacterBody3D`), а не курсор:
ходит по внутренней поверхности вращающегося на 60-метровом радиусе тороидального
кольца (000), смотрит мышью, взаимодействует с окружением через прицеливание
перекрестьем и нажатие клавиши, и работает с семью рабочими панелями рубки как с
физическими объектами через рендер их UI на 3D-меш. Расстояние между панелями —
явный игровой ресурс (время), что превращает многозадачность (система 041) в
физическую, а не в переключение вкладок.

## Player Fantasy

- **Тело вместо курсора.** Чтобы посмотреть в журнал передачи, оператор обязан
  встать и подойти — расстояние между панелями стоит времени.
- **Достоверность вращающегося дома.** «Низ» — не константа, а функция положения:
  за каждый пройденный по кольцу метр игрок поворачивается на 0.955°; пол уходит
  вверх впереди и позади. Должно читаться, не вызывая дискомфорта.
- **Руки вместо интерфейса.** Панели — физические объекты в комнате: навёл
  перекрестье, нажал. Промахнуться, не туда посмотреть — осмысленные состояния
  игры, не баг.

## Detailed Design

### Core Rules

1. **Игрок — дочерний узел вращающегося кольца.** Вся математика скорости ведётся
   в системе координат кольца (которая для этой цели считается инерциальной) и
   переводится в глобальные координаты один раз за кадр, вокруг `move_and_slide()`.
   Это несущее архитектурное решение, а не деталь реализации (см. также
   ADR о системе координат кольца).
2. **Непрерывная переориентация базиса.** Каждый физический кадр направление
   «вверх» берётся из контракта 000 (`get_gravity_up_at()`), базис игрока
   переортонормировывается, сохраняя направление взгляда (см. Formulas).
3. **Локомоция.** Ходьба (2.0 м/с), бег по Shift (3.6 м/с), прыжок (0.68 м при
   0.3 g — втрое выше и дольше земного), пороги до 0.35 м, уклоны до 46° без
   прыжка. Спавн и телепорт в любую из 8 арок программно по ID модуля.
4. **Обзор.** Мышь, чувствительность 0.15°/px (настраиваемая), тангаж [−89°,+89°],
   рыскание без ограничений, FOV по умолчанию 75° (настраиваемый), опциональное
   отключаемое покачивание камеры.
5. **Универсальное взаимодействие.** Луч из центра экрана длиной 2.0 м; любой
   интерактивный объект наследует `Interactable` (`can_interact()`, `interact()`,
   текст подсказки). Подсказка вида «[E] <действие>» появляется при наведении в
   пределах дистанции.
6. **Двери и люки.** 8 дверей на стыках арок — открываются/закрываются
   взаимодействием, переключая коллизию створки. Люки в спицы — заперты, отказ с
   информативным сообщением (задел под EVA).
7. **Рабочая панель как каркас.** `WorkPanel` рендерит свой UI из `SubViewport` на
   плоский меш (0.60×0.45 м, 1024×768), переводит точку попадания луча в пиксель
   вьюпорта, транслирует ввод как штатные события мыши — так что обычный `Control`
   работает без доработок. Семь панелей рубки смонтированы с заглушками «НЕТ
   СИГНАЛА»; одна (диагностическая) полностью рабочая — доказательство каркаса.
   Панель принимает содержимое извне через `set_ui_scene()`/`get_ui_root()` без
   изменения собственного кода — так добавляются будущие панели (021, 022, 024,
   025, 027, 029, 039).

### States and Transitions

| Состояние | Переход в | Условие |
|---|---|---|
| Игрок: идёт / бежит / стоит / в прыжке | между собой | ввод движения + `is_grounded()` |
| Дверь: закрыта ↔ открыта | по `interact()` | взаимодействие в пределах 2.0 м |
| Люк спицы: заперт (терминальное) | — | взаимодействие всегда отклоняется с подсказкой отказа |
| Панель: заглушка «НЕТ СИГНАЛА» ↔ содержимое | по `set_ui_scene()` | вызов другой системы (021…039), не игрока напрямую |
| Захват ввода панелью: свободен ↔ захвачен | `request_input_capture(bool)` | панель запрашивает; пока захвачен — перемещение/обзор игрока подавлены |
| Отладочная камера ↔ камера игрока | программное переключение | **не реализовано** (FR-51, см. Acceptance Criteria — известное отклонение) |

## Formulas

The [ring-up-direction] formula is defined as:

`up = -normalize(Vector3(p.x, 0, p.z))` (в локальных координатах кольца, ось вращения — локальная +Y)

**Variables:**
| Variable | Symbol | Type | Range | Description |
|----------|--------|------|-------|-------------|
| Позиция игрока | p | Vector3 | локальные координаты RotatingRing | Точка, для которой считается «низ» |

**Output Range:** единичный вектор, направлен к оси кольца; на оси (`|r|<0.01`) — вырожденный случай (недостижим в этом ТЗ, но проверяется).
**Example:** точка (0,0,60) → `up = (0,0,−1)`. Обязан совпадать с `StationRoot.get_gravity_up_at()` (000) с точностью <0.01°.

---

The [player-basis-reorientation] formula is defined as:

`right = normalize(forward_prev × up)`, `forward = up × right`, `basis = Basis(right, up, -forward)`

**Variables:**
| Variable | Symbol | Type | Range | Description |
|----------|--------|------|-------|-------------|
| «Верх» текущего кадра | up | Vector3 (unit) | из формулы выше | Пересчитывается каждый физкадр |
| Взгляд предыдущего кадра | forward_prev | Vector3 (unit) | `-basis.z` кадра N−1 | Сохраняет направление взгляда при повороте «низа» |

**Output Range:** ортонормированный правый базис на всём пути по кольцу.
**Example:** `up=(0,1,0)`, `forward_prev=(0,0,−1)` → `right=(1,0,0)`, `basis.z=(0,0,1)`. Вырожденный случай (`|forward_prev×up|<1e-4`): `right` берётся с предыдущего кадра.

---

The [reduced-gravity-jump] formula is defined as:

`h = v₀² / (2g)`, `t_air = 2·v₀ / g`

**Variables:**
| Variable | Symbol | Type | Range | Description |
|----------|--------|------|-------|-------------|
| Начальная скорость прыжка | v₀ | float | 2.0 м/с | `PlayerConfig.jump_velocity` |
| Гравитация на полу | g | float | 2.9420 м/с² (000, 0.3g) | Берётся из контракта 000, не из собственной константы |

**Output Range:** при 0.3g прыжок втрое выше и втрое дольше земного эквивалента.
**Example:** `h = 0.6798 м`, `t_air = 1.3596 с` (при 1g было бы `h=0.2039 м`, `t_air=0.4079 с`).

---

The [panel-hitpoint-to-pixel] formula is defined as:

`u = p_local.x / w + 0.5`, `v = 0.5 − p_local.y / h`, `px = u·vw`, `py = v·vh`

**Variables:**
| Variable | Symbol | Type | Range | Description |
|----------|--------|------|-------|-------------|
| Точка попадания (локально) | p_local | Vector2 | в пределах ±w/2, ±h/2 | Плоскость XY панели, точка вне поверхности даёт (−1,−1) |
| Физический размер панели | w×h | float, float | 0.60×0.45 м | `PanelConfig.surface_size` |
| Разрешение вьюпорта | vw×vh | int, int | 1024×768 | `PanelConfig.viewport_size` |

**Output Range:** `px∈[0,vw]`, `py∈[0,vh]` внутри поверхности.
**Example:** `p_local=(0,0)` → `(512.0, 384.0)`; `p_local=(0.30,−0.225)` → `(1024.0, 768.0)`.

---

The [interactive-element-angular-size] formula is defined as:

`θ = 2·atan(s / (2d))`, пикселей = `θ / (FOV_h / ширина_экрана)`

**Variables:**
| Variable | Symbol | Type | Range | Description |
|----------|--------|------|-------|-------------|
| Размер элемента | s | float | ≥0.04 м (минимум) | Минимальный интерактивный элемент панели |
| Рабочая дистанция | d | float | 0.8–1.5 м | Расстояние оператора до панели |

**Output Range:** на нижней границе рабочего диапазона (0.04 м, 1.5 м) — 39.1 px при FOV 75°, 1920 px ширины экрана — принято как порог уверенного попадания прицеливанием головой.
**Example:** элемент 0.02 м на 1.5 м даёт только 19.6 px — отвергнуто как «на грани промаха».

## Edge Cases

- **If** `forward_prev` почти параллелен `up` (`|forward_prev × up| < 1e-4`),
  **then** `right` берётся со значения предыдущего кадра, `forward` пересчитывается
  от него — базис остаётся валидным вырожденным случаем, а не NaN.
- **If** игрок стоит без ввода, **then** смещение <0.01 м за 10 с и дрейф радиуса
  <0.05 м за 5 минут (устойчивость кольца как системы отсчёта) — **известное
  отклонение**, см. Acceptance Criteria.
- **If** взаимодействие происходит за пределами дистанции 2.0 м, даже если луч
  визуально попал в объект, **then** взаимодействие отклоняется.
- **If** люк ведёт в спицу/ступицу, **then** взаимодействие никогда не открывает
  его и выдаёт подсказку об отказе, сигнал `activated` не испускается.
- **If** панель запросила захват ввода (`request_input_capture(true)`), **then**
  перемещение и обзор игрока полностью подавлены до `request_input_capture(false)`.
- **If** покачивание камеры (`bob_enabled`) выключено, **then** траектория камеры
  строго детерминирована при одинаковой последовательности ввода — **частично
  подтверждено с отклонением**, см. Acceptance Criteria (NFR-09).

## Dependencies

**Зависит от**: 000 (Игровое окружение) — версии 0.3+, должна быть реализована

## Tuning Knobs

| Knob | Where | Safe Range | Too Low | Too High |
|---|---|---|---|---|
| `walk_speed`, `run_speed` | `PlayerConfig` | 1.2–4.5 м/с | Утомительно медленное перемещение между панелями | Расстояние между панелями перестаёт быть ресурсом времени |
| `mouse_sensitivity`, `fov_deg` | `PlayerConfig` | 0.05–0.4 °/px; 60–90° | Обзор ощущается вялым / узкий FOV | Обзор дёргается / искажение по краям |
| `bob_amplitude_v/h` | `PlayerConfig` | 0–0.05 м | Ходьба ощущается «на рельсах» | Дискомфорт, читается как баг камеры |
| `min_element_size_m` (панели) | `PanelConfig` | ≥0.03 м на рабочей дистанции 1.2–1.5 м | Промахи при прицеливании головой | Панели становятся визуально грубыми |
| `interact_range` | `InteractionConfig` | 1.5–2.5 м | Нужно вплотную подходить к каждой двери | Взаимодействие «сквозь» соседние объекты |

## Visual/Audio Requirements

- Игрок бестелесен (нет модели персонажа, рук, тени, анимаций) — осознанное
  упрощение MVP, до отдельной арт-задачи.
- Диагностическая панель: жёлтая рамка, заголовок «ДИАГНОСТИКА / ТЗ-100», кнопка,
  переключатель, ползунок, текстовое поле — единственная панель с реальным
  содержимым, доказывающая каркас.
- Шесть панелей-заглушек показывают «НЕТ СИГНАЛА» с указанием ответственной
  системы.
- Звук отсутствует по скоупу этой системы — только сигналы объявлены (`footstep`,
  `Door.state_changed`, `WorkPanel.activated`), ни одного `AudioStreamPlayer` в
  проекте (проверяется автотестом).

## UI Requirements

Минимальный HUD взаимодействия: перекрестье (меняет состояние при наведении на
интерактивный объект) и одна строка текстовой подсказки вида «[E] <действие>».
Отладочный оверлей 000 дополнен блоком игрока: текущий модуль, локальное
положение, радиус, «низ», скорость, признак опоры, текущая цель взаимодействия.

📌 **UX Flag**: реальные экранные UI появятся только вместе с содержимым каждой
панели (021…039) — для них следует запускать `/ux-design` в соответствующей
эпике, а не здесь; эта система задаёт только физический каркас панели.

## Acceptance Criteria

- **GIVEN** игрок проходит полный круг по кольцу (376.99 м), **WHEN** измеряется
  признак опоры и радиус, **THEN** опора истинна на каждом кадре, радиус
  60.00 ± 0.05 м. — ⚠️ **известное отклонение**: тангенциальный дрейф от пересчёта
  контакта Jolt с вращающимся полом даёт до 0.87 м смещения за 10 с покоя (допуск
  <0.01 м) и до ~4.8–4.9° расхождения азимута за полный круг (допуск ±0.5°); корень
  — R-03/R-04 полного ТЗ, резервная мера («компенсировать поворот родителя явным
  домножением скорости на дельту базиса») не реализована.
- **GIVEN** игрок наводит перекрестье на кнопку диагностической панели и нажимает,
  **WHEN** событие доходит до `SubViewport`, **THEN** кнопка меняет состояние и
  счётчик нажатий увеличивается. — ✅ подтверждено живым запуском end-to-end.
- **GIVEN** дверь на стыке арок, **WHEN** `trigger_interact()` вызван дважды,
  **THEN** дверь открывается со снятием коллизии, затем закрывается с
  восстановлением. — ✅, но с архитектурным пробелом: проём открыт на всё сечение
  трубы, створка меньше — дверь не перекрывает проём физически (осознанно отложено
  пользователем в сессии реализации, не переделывается этим ТЗ).
- **GIVEN** программное переключение между `DebugFlyCamera` и камерой игрока,
  **WHEN** запрошено, **THEN** активная камера меняется. — ❌ **не реализовано**
  (FR-51) — в кодовой базе нет метода/свойства переключения; помечено как
  единственное полностью не выполненное (не частично) требование.
- **GIVEN** две идентичные последовательности программного ввода при
  `bob_enabled = false`, **WHEN** сравниваются траектории, **THEN** совпадают до
  1e−4 м. — ⚠️ расхождение до ~0.97 м между прогонами (NFR-09), причина не
  диагностирована в исходной сессии реализации, вероятно тот же источник шума
  позиции, что и выше.
- Полная таблица критериев со статусами (15 из 21 автотеста ТЗ-100 проходят;
  T-20, T-24, T-25, T-28, T-31, T-36 не проходят) — раздел 10 и 16 полного ТЗ-100.
  Принято к реализации **с задокументированными отклонениями**, не как блокер.

## Open Questions

- **Q-01** Свободный курсор (текущее решение) или фокус-режим с пристыковкой
  камеры к панели? Свободный курсор принят для MVP; `WorkPanel` спроектирован так,
  что фокус-режим добавляется без переписывания содержимого панелей — пересмотреть
  если R-02 (плотные панели вроде дешифратора/звёздной карты утомительны для
  прицеливания головой) подтвердится на практике.
- **Q-03** Открывать ли доступ в спицы/ступицу с невесомостью? Отложено до системы
  014 (EVA) — люки остаются заперты, невесомость не моделируется.
